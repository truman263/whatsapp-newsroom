# Round 8A — Production hardening, recovery and operations architecture

Status: architecture proposal for supervisor freeze. This round changes this document only. Production remains **NO-GO**. No worker, retry, migration, deployment or production credential is authorized here.

Baseline: `feat/round-8-production-hardening` at `ab149652c62793163889bfbfd5c26a1fd777895b`. The local Round 7 branch has that same commit; no remote Round 8 branch existed at preflight. Round 7 engineering is complete, but its callable drivers are not an always-running production service.

## 1. Source audit and precedence

Audited the roadmap, general architecture, invariants, security, and frozen Round 4–7 architectures against the current Prisma schema and the ingestion, reporter workflow, story collection, media staging/Meta client, draft/media WordPress clients, draft preparation, preview, outbound, approval, publication, configuration and logging sources. Later frozen Round 2B–7 contracts supersede older roadmap/security statements about generic WordPress Application Passwords: the implemented WordPress authorities are separate route-scoped HMAC credentials and service identities. No generic WordPress credential is a recovery fallback.

Current concrete seams: inbound `claim(eventId)` conditionally changes `RECEIVED→PROCESSING`, increments `processingAttempts` and sets `processingStartedAt`; its anti-join blocks a later same-sender `RECEIVED` event behind every earlier `RECEIVED` or `PROCESSING` event. `process(eventId)` has narrow Round 6 preparation and Round 7 Approval lineage resume, but no generic abandoned claim reclaim. Media staging conditionally claims `RECEIVED→FETCHING`, stores bytes at `story-media/v1/{StoryMedia.id}/source`, and leaves its inbound event `PROCESSING` until `FETCHED` or definitive failure. Round 6 `recoverUnfinished` scans `ACTIVE` and `RECONCILIATION_REQUIRED` preparations, but has no production scheduler. Outbound dispatch claims `PENDING→SENDING`; uncertain sends remain `SENDING`, and `recoverUncertainSend` returns `MANUAL_RECONCILIATION_REQUIRED`. The outbound request sends no proven provider-side idempotency key or recoverable correlation that could prove a lost response. The Round 7 driver scans only `PENDING/IN_PROGRESS` PUBLISH attempts; its saga performs GET-first recovery and never auto-claims `RECONCILIATION_REQUIRED`.

The existing schema has inbound status/start/attempt fields and useful inbound/draft/publish indexes. `processingAttempts` is the frozen generation fence once every continuation compares it; current code does not yet do that. The schema lacks `InboundEvent.processingContractVersion`, the required 8B.0 prerequisite for safe cross-version stale recovery. `StoryMedia` has only a status index, not a status/age index; `OutboundMessage` has `(status,requestedAt)` but not `(status,updatedAt)`. `updatedAt` is a mutation timestamp, not proof that an external call is over. Current `UnconfiguredMediaObjectStore` fails closed and cannot support production; §5 freezes the required private S3-compatible adapter. The general `SECURITY.md` and roadmap contain historical statements; this document does not silently reactivate them.

## 2. Scope, non-goals and authority hierarchy

Round 8 designs bounded ordinary work scheduling, lineage-aware stale recovery, external uncertainty handling, operator reconciliation, telemetry, release controls and load/fault proof. It does not authorize new editorial commands, replay historical terminal events, reinterpret old content under new rules, alter Round 5–7 authority, or infer remote success from timestamps, Story status, Conversation state, process memory, HTTP history, or WordPress post status.

Authority is, in order: the authenticated durable `InboundEvent` and its claim generation; a Story mutation committed atomically with its event terminal update; `StoryMedia` plus its owning event and deterministic object key; `DraftPreparation` plus immutable Story epoch and CREATE/SYNC attempts; linked `OutboundMessage` plus its prompt binding; immutable `Approval` plus its one PUBLISH `PublishAttempt`; and the exact WordPress publication ledger. Age selects candidates **for inspection**, never supplies authority. A downstream row is never synthesized merely because a parent is old. External reads occur outside PostgreSQL transactions; local transitions revalidate under short transactions and canonical locks.

## 3. Complete status policy

Abbreviations: O = ordinary scheduling; S = stale inspection; A = automatic retry/resume after exact authority checks; G = GET/reconciliation first; P = operator only; T = terminal. “Bounded” always means configuration-governed attempts and backoff (§10). A status alone never grants action.

| Aggregate/status | O/S/A/G/P/T | Authority, allowed target, failure/audit posture |
|---|---|---|
| Inbound `RECEIVED` | O yes; S no; A claim; G no; P on poison; T no | Authenticated event, ordered anti-join and generation-fenced claim → `PROCESSING`; fixed claim/ignore codes, no poll audit. |
| Inbound `PROCESSING` | O no; S yes; A lineage-dependent; G for external lineage; P if ambiguous/exhausted; T no | Event + generation + exact downstream rows. Resume in place; **never generic reset to RECEIVED**. Proven no-lineage work may be fenced and restarted only under §4. Exhaustion → supervised `FAILED`, fixed code/audit; never overtake. |
| Inbound `PROCESSED` | O/S/A no; T yes | Immutable completion evidence; never replay, scan or reset. |
| Inbound `FAILED` | O/S/A no; P diagnostic only; T yes | Terminal bounded/poison result with fixed reason; later sender may proceed; no blind replay. |
| Inbound `IGNORED` | O/S/A no; T yes | Terminal policy result; later sender may proceed; no retry. |
| Media `RECEIVED` | O via owning event; S yes; A bounded; G object HEAD first; P on conflict; T no | Exact StoryMedia/event/Story ownership, deterministic key → `FETCHING`; media recovery audit only on decision. |

No blind overwrite. |

Unknown outcome stays reconciliation-required at preparation level. |

| Preparation `SUPERSEDED` | O/S/A no; T yes | Old prompt/preview authority invalid; never reactivate. |
| Preparation `FAILED` | O/S/A no; P diagnosis; T yes | Local corruption/terminal supervised decision; no automatic new preparation. |
| Outbound `PENDING` | O yes; S no; A single claim; G preview/epoch revalidation; T no | Exact linked prompt/correlation and valid preview; `PENDING→SENDING`, increment `sendAttempts`; fixed send audit. |
| Outbound `SENDING` | O/A no; S yes; G only if a **verified** provider correlation contract is later approved; P now; T no | Lost acceptance response is indistinguishable from nonacceptance. | Outbound `SENT` | O/A no; T for send phase | Provider ID persisted; delivery webhook may move to `DELIVERED`; no duplicate send. |
| Outbound `DELIVERED` | O/S/A no; T yes | Provider-delivery evidence; no resend. |
| Outbound `FAILED` | O/A no; P explicit proof/decision; T to ordinary work | Definitive rejection only. A new send intent, if ever authorized, requires a separate approved contract; do not silently reset. |
| PUBLISH attempt `PENDING` | O yes; S yes; A same-attempt claim; G before POST in saga; T no | Exact Approval/epoch; claim → `IN_PROGRESS` with Story/Conversation PUBLISHING. |

| PUBLISH attempt `RECONCILIATION_REQUIRED` | O/A no; S alert only; G supervised mandatory; P yes; T no | Same attempt; matching PUBLISHED ledger may finalize. Exact repaired draft may explicitly resume same attempt. No new attempt. |
| PUBLISH attempt `FAILED` | O/S/A no; P terminal review; T yes | Unrecoverable local corruption or supervised failure, Conversation attached, event PROCESSING. |
| PUBLISH attempt `SUCCEEDED` | O/S/A no; T yes | Story PUBLISHED, Conversation IDLE/null, event PROCESSED; ledger-backed read-only replay. |

| `DRAFT_CREATED` | Exact preparation may GET/sync/finish toward `AWAITING_APPROVAL`; no version bump. |
| `AWAITING_APPROVAL` | Exact prompt or explicit revision/approval event only; recovery cannot approve from status alone. |
| `APPROVED` | Exact Approval-bound PENDING attempt may claim toward `PUBLISHING`. |
| `PUBLISHING` | Exact IN_PROGRESS attempt/ledger proof may finalize to `PUBLISHED`; uncertainty stays blocking. |
| `PUBLISHED` | Terminal/read-only; no automatic unpublish. |
| `CANCELLED` | Terminal; no revival. |
| `FAILED` | Operator-only diagnosis; no generic backward reset. |

| Conversation state | Recovery cross-check |
|---|---|
| `IDLE` | No current Story; never infer new work. |
| `AWAITING_HEADLINE` | Only exact ordered inbound event may supply headline; no status-only replay. |
| `AWAITING_BODY` | Only exact ordered inbound event may supply body. |
| `COLLECTING_MEDIA` | Exact category/media/finalisation lineage only. |
| `AWAITING_APPROVAL` | Exact current preparation/prompt, revision or Approval event only. |

All Story/Conversation work inherits the owning durable row's retry budget, audit, fixed code and GET rule. Every backwards transition not explicitly frozen in Round 4–7 is prohibited.

Matrix-wide operational contract: every permitted automatic transition uses a configured per-phase cap and §8 backoff; terminal, operator-only and alert-only rows have a zero automatic-retry budget. A successful conditional claim or state change records a fixed subsystem/action audit event, while a no-op poll or lost CAS does not. Failures use fixed `TRANSIENT_LOCAL`, `TRANSIENT_REMOTE`, `UNCERTAIN_EXTERNAL_OUTCOME`, `DETERMINISTIC_USER_ERROR`, `DETERMINISTIC_INVARIANT_FAILURE`, `AUTH_CONFIGURATION_FAILURE` or `OPERATOR_RECONCILIATION_REQUIRED` codes, refined into subsystem-specific allowlisted codes in 8B.0; never persist free-form provider text as a machine code. The target column above is exhaustive for ordinary work, not permission to invent a missing transition. A remote GET is mandatory before repeating any uncertain WordPress mutation and before publication `IN_PROGRESS` continuation; GET-only inspections cannot themselves promote an ambiguous row. Every exception and cap exhaustion retains the same durable authority and an operator-visible outcome, with no silent drop or backward reset.

## 4. Inbound stale claim and sender ordering

Staleness uses `processingStartedAt < now - configured_stale_interval`, never `updatedAt`. Interval, attempt cap and safety margin are validated, bounded deployment configuration tuned from 8B.5 evidence; age cannot prove worker death. `processingAttempts` remains monotone and never resets. Every successful initial `RECEIVED→PROCESSING` claim and eligible stale `PROCESSING` reclaim atomically increments it, refreshes `processingStartedAt`, and returns the new value as the claim token. Every subsequent local transaction capable of changing state on behalf of that event must lock/check `InboundEvent.id`, `processingStatus=PROCESSING`, and `processingAttempts=expected claim token` before commit. An old token cannot commit after reclaim. PostgreSQL claims/fences, not memory locks, provide correctness. The current Int field suffices for the bounded generation, but enforcing this contract in every continuation is an 8B.1 implementation and rolling-deployment gate.

`InboundEvent.processingContractVersion` is the mandatory 8B.0 schema prerequisite: a nullable integer processing-contract identifier for migration/adoption, never inferred from deployment time. The first successful ordinary claim records the currently supported contract if the field is null; an unclaimed `RECEIVED` row may thus be handled under the running contract. A stale `PROCESSING` row is automatically recoverable only if its stored non-null version is explicitly supported by the worker. Legacy null and unsupported versions are operator-held until evidence-backed supervised/terminal action. Historical `PROCESSED`, `IGNORED` and `FAILED` rows are never replayed. Contract support must be an explicit code compatibility decision, not a timestamp guess.

Candidate scan: `PROCESSING` by `(processingStatus,processingStartedAt,id)`, bounded oldest first. In one short transaction lock the event; reread status, expected `processingAttempts`, same-sender predecessor and exact downstream lineage. Twenty workers may inspect, but only one compare-and-increment claim wins. Never use sequence arithmetic: any earlier `RECEIVED/PROCESSING` row blocks later work; gaps are harmless. A terminal `PROCESSED/IGNORED/FAILED` predecessor unblocks the next row. Do not mark a stranded predecessor `FAILED` solely to increase throughput.

Lineage routing classifies before acting, in authority order: (a) Approval/PUBLISH attempt: resume only the existing Round 7 attempt; (b) DraftPreparation: resume its existing Round 6 epoch; (c) StoryMedia: verify the same media/event/object/Story and use media-specific recovery; (d) already-atomic Story mutation evidence: do not replay the user mutation; (e) no committed downstream lineage: wait for any current transaction lock, then resume the same event only with a supported stored `processingContractVersion` and newly fenced claim token. An uncertain external side effect always follows its subsystem GET/reconciliation rule first; ambiguity remains blocking/operator-held. A `PROCESSING` event can never be generically changed to `RECEIVED`: an old worker could observe the newly claimed `PROCESSING` row and act without distinguishing ownership. Existing Stage 5 `/story`, headline, body, category replacement and `/cancel` commit mutation and terminal event atomically, so a committed mutation is already terminal; uncommitted mutation rolls back. Image staging deliberately spans phases. `/done` has a durable preparation; `/approve` has a durable Approval after its atomic commit. Never reinterpret stale user text under an unsupported processing contract.

Exhaustion is not permission to abandon: a generation-fenced transaction records a fixed machine code and audit and may set `FAILED` only for a proven no-side-effect/poison event. If external lineage or outcome is uncertain, leave `PROCESSING` and raise an operator reconciliation case. The sender remains blocked until an evidence-backed terminal decision.

## 5. Media and WordPress draft recovery

`RECEIVED/FETCHING` recovery checks exact event/Story ownership and deterministic object HEAD, then streams/read-verifies bytes, SHA-256, MIME, size and configured ceiling. A matching object closes the crash-after-write window without Meta redownload. An absent object permits bounded secure Meta refetch only after ownership fencing; a conflicting object is operator-only and is never overwritten. Crash before/during metadata/download leaves no durable byte proof; crash after `FETCHED` may complete the same inbound event idempotently. Preserve HTTPS, DNS pinning, private-address/redirect refusal, bounded response, fixed host/token forwarding, MIME/magic and checksum checks for old jobs exactly as for new ones.

`UPLOADING` is also a Round 8 recovery concern: Round 6 sets that status around WordPress media work. GET the deterministic WordPress media key before another POST. Matching media reconciliation evidence plus exact local bytes/metadata permits persisting the same WordPress ID; conflicting/malformed evidence blocks. For CREATE_DRAFT, GET the permanent `Story.wordpressDraftKey`; for SYNC_DRAFT, GET authoritative full state and compare applied version and six-field fingerprint before any PUT. Reuse the existing CREATE/SYNC PublishAttempt identity. `ACTIVE` work may be scheduled, and `RECONCILIATION_REQUIRED` may be inspected GET-first, but neither age nor retry count creates another preparation, Story epoch or WordPress post. `BLOCKED` needs operator repair; `SUPERSEDED`, `READY_FOR_APPROVAL`, `FAILED` are not recovery work. All HTTP remains outside PG transactions.

Production staging uses a **private S3-compatible durable object-store adapter**; the vendor is deployment configuration, not an architecture decision. The adapter requires TLS, server-side encryption, deterministic keys, conditional create/put-if-absent, HEAD metadata, durable read-after-write sufficient for verification, byte reads, exact size, MIME metadata and SHA-256 verification. It must deny public ACLs, enforce an explicit lifecycle/retention policy, use explicitly configured credentials and never log them. `UnconfiguredMediaObjectStore` remains a fail-closed test binding and fails the production activation gate. Implement and prove the adapter in 8B.2.

## 6. Outbound and publication recovery

The current Meta outbound send persists `SENDING` before HTTP and `providerMessageId` only after a successful response. It does not send a verified idempotency token or persist a provider-issued ID before acceptance. A response lost after Meta accepts is therefore indistinguishable from a request Meta never accepted. **Supervisor decision: no automatic resend of stale or uncertain `SENDING`.** `PENDING` alone is eligible for ordinary send; `SENT/DELIVERED` are successful, and `FAILED` is reserved for definitive failure where a duplicate external send is impossible. A worker that finds stale `SENDING` without safely proven completion makes no Meta send call and atomically confirms `status=SENDING`, `lastErrorCode=WHATSAPP_SEND_OUTCOME_UNCERTAIN`, `lastErrorMessage=null`; the first conditional transition into that held posture writes one durable recovery/operator-needed audit in the same transaction and surfaces the hold in metrics, alerts and the operator queue. Repeated scans that find the held code are no-ops and do not multiply audits. `sendAttempts` is not a deduplication key; `updatedAt` indicates age only. Operators cannot fabricate `SENT`, reset `PENDING`, or issue a duplicate prompt on guesswork. No new outbound status is needed for Round 8. A future genuinely durable Meta correlation/idempotency contract would require a separate architecture change, not an assumed capability.

PUBLISH recovery stays exactly Round 7: scheduler selects only `PENDING/IN_PROGRESS` PUBLISH attempts in stable bounded order, and the saga revalidates immutable Approval/Story/Conversation bindings. Every `IN_PROGRESS` re-entry GETs `publish_key` before POST. Only exact PUBLISHED ledger evidence finalizes Story/Conversation/event. `RECONCILIATION_REQUIRED` never enters ordinary scheduling; supervised GET-first reconciliation may finalize the same attempt or, after exact repaired approved draft proof, explicitly resume it. `FAILED/SUCCEEDED` are terminal. No publish logic is copied into a generic recovery worker.

## 7. Scheduler topology, scans and claims

Use a **dedicated worker process/entry point**, optionally the same codebase/image as the API but separately deployed. The API process owns no periodic recovery loops. Multiple worker replicas are allowed; PostgreSQL claims/fences provide correctness and no process-local singleton is required. A thin orchestrator delegates to existing/approved subsystem services without copying media, draft, outbound or publish business rules. Its separate bounded loops are: ordinary `RECEIVED` inbound processing; stale `PROCESSING` recovery; media recovery; DraftPreparation recovery; outbound `PENDING` dispatch; stale `SENDING` uncertainty surfacing; and PUBLISH `PENDING/IN_PROGRESS` driving. Frozen `RECONCILIATION_REQUIRED` exclusions remain intact. API readiness depends on safe durable ingestion, not WordPress/Meta availability. Worker readiness requires database connectivity, valid configuration and a recent successful scheduling cycle; downstream outage is reported as degradation/alerts, not false webhook failure.

Each loop has configurable cadence, bounded batch, per-subsystem and global concurrency caps, jitter, error backoff and graceful stop. No process-local mutex is correctness authority. DB conditional update, row locks and unique keys decide claims; `SKIP LOCKED` may be used only for short candidate/claim transactions, never held across HTTP. A crashed scan is harmless because it owns no durable authority. Overlapping replicas can select the same IDs and must converge through CAS. Start workers only after compatible migrations and code are deployed; do not run old/new workers on incompatible status semantics.

| Scan | Ordering/index | Claim and failure handling |
|---|---|---|
| ordinary inbound `RECEIVED` | `(processingStatus,receivedAt,id)` plus sender sequence anti-join; current index starts `(processingStatus,receivedAt)` | bounded IDs, invoke existing ordered conditional claim; blocked sender remains queued, other senders progress. |
| stale inbound `PROCESSING` | `(processingStatus,processingStartedAt,id)`; current two-column index | generation-fenced row claim proposed; lineage router; no reset/replay of terminal events. |
| StoryMedia `RECEIVED/FETCHING/UPLOADING` | propose `(status,updatedAt,id)`; existing status-only index is inadequate for age-ordered large scans | inspect exact owner and object/WP key, conditional status/generation claim; conflict → operator. |
| DraftPreparation `ACTIVE/RECONCILIATION_REQUIRED` | current `(status,updatedAt)` | bounded stable ID selection; same-epoch revalidation; GET-first on uncertainty; `BLOCKED` alert-only. |
| Outbound `PENDING/SENDING` | PENDING current `(status,requestedAt)`; propose `(status,updatedAt,id)` for stale SENDING | PENDING uses existing dispatch CAS; SENDING inspection/alert only, never auto resend. |
| PUBLISH `PENDING/IN_PROGRESS` | current `(operation,status)` and `(status,createdAt)`; propose composite `(operation,status,createdAt,id)` if plan/load shows need | existing driver/saga CAS; no reconciliation-required claim. |

Use measured query plans before adding indexes. Candidate selection is bounded, not a lock across network work. Stable UUID tie-breakers prevent starvation. A persistent hot/poison candidate must be moved to an evidence-backed blocking state/alert or governed by eligible-at scheduling, never silently skipped forever.

## 8. Retry, timing and exhaustion

| Class | Automatic action | Exhaustion/alert |
|---|---|---|
| TRANSIENT_LOCAL | bounded retry after rollback and fresh DB authority read | fixed local code; operator if cap reached |
| TRANSIENT_REMOTE | retry reads; mutation only if idempotency/reconciliation proves safe | degraded dependency alert, same durable row |
| UNCERTAIN_EXTERNAL_OUTCOME | GET/reconcile first, never blind mutation retry | reconciliation/operator state, high-severity alert |
| DETERMINISTIC_USER_ERROR | none; terminal `IGNORED` where frozen semantics permit | content-free informational audit |
| DETERMINISTIC_INVARIANT_FAILURE | none | `FAILED` only where frozen; security/operations alert |
| AUTH_CONFIGURATION_FAILURE | none until configuration repaired | `BLOCKED` or reconciliation posture; alert, no secret logs |
| OPERATOR_RECONCILIATION_REQUIRED | none | operator queue; never auto-age into success/failure |

Backoff is bounded exponential `min(maxDelay, initialDelay × 2^(attempt-1))` with full jitter in `[0,delay]`, configurable initial/max delay, attempt cap and per-dependency concurrency. Stale `PROCESSING` and `SENDING` thresholds, polling cadence, initial/max retry delay, jitter, batch sizes and concurrency caps are configuration-driven, validated, bounded and observable; exact production values are tuned from 8B.5 load/fault evidence, not invented in 8A. Reset a retry budget only after an independently proved new logical phase or explicit supervised repair; a process restart does not reset it. Current `updatedAt`/attempt fields can derive conservative eligibility for some work, but unrelated writes mean they cannot reliably encode every per-phase time or a durable operator hold. The existing `SENDING` plus fixed error code is the approved hold representation. `nextAttemptAt` or a recovery schedule table is **not pre-authorized**: propose one later only if measured evidence proves current timing cannot satisfy a specific invariant. Do not busy-poll. `processingAttempts` must remain monotone and never silently wrap. Every exhausted item retains a fixed machine-readable code and audit; no work disappears.

## 9. Operator reconciliation

Provide an authenticated, least-privilege operator command/runbook (not a public reporter endpoint). Actions are inspect redacted IDs/status/lineage; GET-only external reconciliation; explicit same-row safe resume after proof; terminal fail where the frozen state machine permits; and record operator identity, reason, before/after status, evidence reference and timestamp in append-only audit. Require a second reviewer for publication and ambiguous outbound decisions. Never expose body, phone, token or media URL in the command output by default. Operators cannot rewrite Approval epochs, fabricate ledger/provider evidence, reset PUBLISHED, bypass ownership, resurrect SUPERSEDED work or generically replay terminal inbound events. For an ambiguous outbound send, the safe default is hold; any deliberate duplicate-risk resend is a **new supervisor-approved product policy**, not a hidden recovery action.

## 10. Observability, logs, audit and health

Metrics: inbound RECEIVED/PROCESSING count and oldest age, recovery outcomes, FAILED/IGNORED; media counts and oldest FETCHING/UPLOADING; preparation ACTIVE age and RECONCILIATION_REQUIRED/BLOCKED/FAILED; outbound PENDING/SENDING age, FAILED/uncertain; publish PENDING/IN_PROGRESS age, RECONCILIATION_REQUIRED/FAILED; scheduler run duration, selected/claimed/blocked counts, conflicts, errors and last successful cycle. Labels are bounded subsystem/status/code only—never phone, Story ID, headline or provider ID. Alert on aged blocked queues, reconciliation growth, retry exhaustion, worker silence, database pool pressure and dependency outages. Define thresholds from measured load and on-call capacity.

Structured logs allow event/attempt UUID, subsystem, fixed code, status, duration, HTTP status, retry count and correlation ID. Deny-list and sink tests must exclude WhatsApp access/app/verify tokens; draft/media/publish/preview HMAC secrets; Authorization, Cookie/nonce headers; raw provider payload; phone; headline/body/byline/caption; temporary Meta URL; media bytes; and WordPress responses that may contain article text. Do not log configuration objects. AuditLog remains append-only application evidence, not authority. Existing security/workflow/external audits are retained; Round 8 adds durable decision-only `inbound_recovery_*`, `media_recovery_*`, `draft_recovery_*`, `outbound_recovery_*`, `publish_reconciliation_*`, `operator_recovery_*`. Do not audit every poll. Review current event names, metadata allowlists and retention with the privacy/security owner before activation.

API liveness is process responsiveness; API readiness is ability to authenticate and durably store an inbound event in PostgreSQL. WordPress, Meta send, media store or worker degradation does not turn a safely persisted webhook into a failed 200/503 decision. Worker liveness is loop responsiveness; readiness fails on invalid config/DB or a non-running loop, while external outages are dependency degradation and alerts. On SIGTERM stop claims, finish/rollback short PG transactions, give bounded external operations their configured timeout, and leave every unfinished action in its pre-existing durable intent/uncertain posture. No in-memory ownership is required for restart correctness.

## 11. Security and load proof plan

Threat classification: **CRITICAL: none identified in this architecture audit**. **HIGH-impact prohibited scenarios:** generic inbound `PROCESSING→RECEIVED` replay and blind resend of uncertain outbound `SENDING`; both are explicitly forbidden, not open product defects. **Blocking MEDIUM for production activation, not for 8A freeze:** missing worker/recovery implementation, S3-compatible adapter, monitoring/alerts and fault/load proof. **Non-blocking MEDIUM for 8A:** production scan-index and pool sizing pending 8B.0/8B.5 evidence. **LOW:** telemetry/cardinality risk with enforced allowlists. Existing code does not currently perform the unsafe reset/resend; these are implementation/activation gates, not a claim of a presently exploitable publish bypass. Test retry/replay amplification, stale authority, cross-Reporter recovery, lock starvation, poison sender, SSRF in old media jobs, credential leakage, operator privilege, duplicate scheduler execution, DB pool exhaustion, repeated webhook replay, WordPress and Meta outages.

Acceptance uses invariants first: 20+ stale-event contenders yield one fenced owner; same-sender burst never overtakes unresolved predecessor; many senders progress independently; media/draft/outbound/publish contention creates no duplicate external authority; overlapping scheduler scans converge; no remote I/O under PG locks; bounded connection/concurrency usage; no secret/content telemetry. Inject crash at every durable boundary, including object write, WordPress CREATE/SYNC/media/publish commit and Meta accepted-but-response-lost. Quantitative latency/throughput targets are deferred until production topology and capacity are specified; measure p50/p95/p99, backlog drain and query plans on disposable/staging equivalents, not live traffic in 8A.

## 12. Schema sufficiency, rolling deployment and release gate

**Current schema is insufficient for the frozen cross-version recovery contract, but sufficient for claim-generation fencing.** 8B.0 is authorized to propose/implement the minimal prerequisite `InboundEvent.processingContractVersion Int?`: nullable integer for migration/adoption, with first successful ordinary claim filling null and no timestamp-derived backfill. Legacy stale null/unsupported-version `PROCESSING` remains operator-held; terminal historical events remain terminal.
